# First playable carry slice: hold to hand to buyer

**Proposed M1 repair slice.** The player can retrieve catch stranded in a boat, carry it ashore, put it into a small tote or a counter's receiving pan, and sell only that delivery. The proof starts with a catch already in the hold; it does not need a new fishing method, vehicle, general inventory editor or automatic route. It must preserve reload safety. The wider ban on automatic landing/banding/freezer batches is a separate intake follow-up, GH-04, before the handling conversion is declared complete.

Use [ADR 0043](../../adr/0043-input-intents-and-bindings.md)'s existing `Interact` intent, default keyboard **E**, plus the existing movement bindings and the current binding-driven prompt glyph. Do not invent a key or hardcode a gamepad button. `IInteractable` / `InteractResolver`, `InteractOffer`, `InteractionGate` and the existing capture/claim rules arbitrate **one** action per press. No new raw-key reader beside boarding and dialogue. Proposed labels below are short text-table entries, not new HUD inventory readouts.

## The player's steps

| Step | Input, target and prompt | State change and owner |
|---|---|---|
| 1. Reach the hold | Moor safely, leave the helm using existing controls, stand on the same boat's deck within the hold opening's measured reach. E: **“Take a fish”**. | gameplay-systems exposes that specific boat instance and its reachable source opening. A wharf-side player cannot select a remote hold. Source choice follows stable stored order; species selection UI is deferred. |
| 2. Take one catch | E commits the offered take. **“Your hands are full”** or **“Use both hands”** explains refusal. | Core validates hands and source revision, then moves one item to the available hand or both hands. Source removes exactly that id only on success. No `Clear`/re-add partial-take workaround. Existing rod/pail stays in its hand; player sets it down first when both hands are needed. |
| 3. Carry ashore | Walk to the boat's existing boarding/disembark point and use its existing E offer, then walk to the buyer. A carried fish remains in hand throughout. | gameplay-systems keeps hand state through deck/shore modes. world-content verifies an actual supported boarding route and landing point at usable tides; gameplay-systems enforces it. If the mooring rope needs a hand, a two-hand load cannot cross until the rope is fast to a cleat. No disappearing rope, air step or reach across the gap. |
| 4a. Put in a tote | Approach a reachable, open small tote. E: **“Put fish in tote”**. On full/shape failure: **“That won't fit”** or **“The tote is full”**. | Core commits hand→container; gameplay-systems implements. Block overflow and keep the fish in hand on refusal. The targeted tote wins over the belt pail; unintentional E stow into a different container is a bug. |
| 4b. Deliver at the counter | Approach the receiving pan. E: **“Set fish on counter”**. | Same hand→container move into this counter's player-owned receiving area. One loose item is enough for the first slice. No payout yet. The pan can be taken from again with **“Take your fish”** before confirming sale. |
| 5. Sell the delivery | Use the existing clerk conversation's sell choice. It quotes only the receiving area. Confirm through that conversation. | economy-sim validates delivered ids, current freshness and market price, removes the accepted selection and credits once. Unsellable fish remains in the pan and can be picked back up; no boat/belt/world-pail lookup fills an empty sale. ui-ux/world-content own quote/refusal text and dialogue. |
| 6. Repeat or move a light tote | E: **“Take the tote”** after setting the fish down, only if hand/gross/envelope rules permit. E at a supported location: **“Set down tote”**. An open tote receiving area may be used as an intermediate store before returning to the hold. | gameplay-systems moves the same container instance and children; lead-architect saves its support and location. Large/full device loads refuse. Selling all contents of a delivered container is a later extension; the first sale proof uses the loose-item pan. |

There is no mandatory floor-drop action in this slice. If a route requires unsupported motion or art/scene work owned by an active lane, that **site** is blocked for integration; exercise the logic against a supported fixture and hand the route gap to world-content. Never “solve” access with a remote transfer. The loop is not player-accepted until one real boat→shore→buyer route is proven.

## Core boundary handoff

Names below are **proposed contracts**, not APIs already present. Lead-architect ratifies names and shape before implementation. Modules reference Core only; App may compose implementations, never make a sale adapter search for another module's concrete inventory.

| System | What it exposes through Core | Implementer / consumer |
|---|---|---|
| Hands | Extend optional hand read/command seams beside `ICatchHands` / `IHandsCarrier`: current occupants, accepted load, take/put result, left/right/both reservation. Keep `HandSlots` continuity and refusal messages. | gameplay-systems implements Player side; transfer authority consumes |
| Hold, pail, tote, freezer, receiving pan | Proposed `IGoodsContainer`: stable instance id, read-only item ids/order, revision, shape/capacity/access snapshot; command intents go to authority. Existing `IHold` remains a compatibility reader until its callers migrate. **No generic remote mutation API granted to the buyer.** | gameplay-systems implements mechanical adapters; economy-sim owns preservation and receiving policy |
| Transfer | Proposed `IGoodsTransfer.TryMove(request)`: transaction id, actor, source/destination, item id, expected revisions and requested placement; typed result. Validates real reach and support, hand policy and freshness-mode transition, then atomically commits. | gameplay-systems implements engine-light service against Core contracts; lead-architect defines contract and composition/save boundary |
| Support and access | Proposed `IGoodsSupport`: region/level/boat or vehicle instance, local support polygon/height, opening state, reachable interaction point. Resolve dynamic parent frame before checking distance. | gameplay-systems implements boat/vehicle access; world-content supplies authored fixtures via Core; art-director supplies measured geometry |
| Buyer | Proposed `IDeliveredGoodsSale`: counter id plus explicitly delivered selection and quote revision. Uses the existing pricing/freshness maths; validates at commit so stale quotes/refused fish cannot be sold. | economy-sim implements; conversation/UI calls Core |
| Persistence | Proposed registry snapshot/load hook covers item and container identity, hand occupancy, supported placements and cold history; transaction snapshot is consistent with money/market. | lead-architect implements save integration/migration; gameplay-systems and economy-sim serialize through that boundary |
| Fill, offers and onboarding | Proposed `GoodsMoved` carries transaction id, item/container ids, source/destination ids and revisions; `GoodsLocationChanged` handles a moved container's frame; a typed rejection supplies a prompt id. Each fires after commit only. | art-pipeline's presenters refresh relevant inventories; ui-ux renders prompts; world-content/onboarding consumes acquisition separately |

Keep `CatchLanded` for new landing and `CatchSold` for completed sale. `FishCaught`'s current “entered hold” use is not replayed for old-stock transfers: migrate fill consumers to `GoodsMoved`, and keep onboarding on true acquisition so moving a clam between two pails never advances a catch task. Rejections publish no success event. No renderer, transaction history or EventBus subscriber is the sole authoritative item store.

## Testable acceptance criteria

1. Given hold item A and free eligible hands, one Interact press removes A from that boat and places **that id** in the hand; total unsold ownership count is unchanged.
2. Given full hands, the same press changes zero item locations, freshness values, money and source revisions; a visible refusal appears. There is no hold/belt fallback.
3. Given a two-hand fish and a rod in one hand, take refuses and the rod's hand/pose ownership does not change. After the rod is set down, the fish occupies both hands.
4. Given a full or incompatible tote, put refuses; A remains held and no floor item is spawned. A length mismatch refuses even when volume/count has spare room.
5. Given a reachable open tote and a catch in hand, E puts the item in that tote; the belt pail receives zero items. A closed tote requires opening first.
6. Given a wharf-side actor outside the boat hold's access frame/reach, no take commits. Closed doors, different storeys and an unusable boarding route also refuse.
7. During boat→deck→shore→buyer movement, A remains attached to the player with one supported carry location; mooring work never silently replaces it or adds a third hand.
8. Before delivery, a clerk's quote and sale consume zero boat, belt-pail, freezer, truck or nearby-tote items. After A is set on its receiving pan, that seller can quote A alone.
9. Delivery changes no money. Sale pays once for selected sellable delivered items using existing marginal pricing; spoiled/refused items remain retrievable, and withdrawing an unsold delivery pays nothing.
10. Moving A repeatedly between hands, pan and tote preserves its size and banked spoil; protected→ambient transitions settle the old mode first. Repeated stow does not refresh a catch or award onboarding progress.
11. Reload with A in hand, in the receiving pan or in a placed tote restores exactly one A, exact size and freshness, hand side/support and tote contents. Cross-region carry retains the same ids.
12. A stale source revision, duplicate request, vanished destination or interrupted animation creates neither a duplicate nor a lost fish nor a second payment; snapshot load yields the entire pre- or post-commit state.
13. One E press performs exactly one offered verb; boarding, a modal conversation and the container cannot all consume it. Binding glyphs follow the active device.
14. Removing the last fish empties its container's visible fill; adding the first shows that species/size group. Rim occlusion and support height are verified by the art roles in the real route, without changing a plate expectation to accept a regression.

Future implementation proof: EditMode exact-count assertions for hand refusal, transaction conservation, save migration and freshness; PlayMode for E arbitration, boat/deck/shore transitions and seller delivery; an actual editor route/fill plate review by the owning art/world roles. **This docs-only lane runs no Unity and claims none of those tests or plates passed.** Existing `HandSlotsTests`, `CarryHandsAnchorTests`, `ClamDigTests`, `FreshnessStampingTests`, `DeckPotStateTests` and sell freshness tests are migration starting points, not permission to weaken assertions. Explicitly replace each pinned direct-hold rule with its new hand/delivery truth and explain why in the implementation PR.
