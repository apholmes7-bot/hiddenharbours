# Carrying an island demo week into the full game

**The save format can represent the saved part of an island week, but the corrected demo configuration keeps it in a separate slot. The full game does not automatically discover or continue that demo file.** The demo uses `demo/savegame.json`; the full game retains `savegame.json`. There is no import feature. Source-level compatibility is not a verified promise that every part of the week restores correctly in a packaged player.

**Lean: retain the separate destinations and add an explicit copy into the full game.** Separation is now implemented in the configuration draft. Discovery, source validation and the player's import choice remain new work. They must protect an existing full-game playthrough and leave the demo source intact. This document changes no path, saved field or runtime behavior.

This document uses pinned main `541276cbc9308ba60ded8b905308366306438570`, whose save version is **25**; the corrected demo configuration in [draft #1510](https://github.com/apholmes7-bot/hiddenharbours/pull/1510), at `2e7adfaeec208b355dbbf949954fd27690224de7`; and the session-only ending proposal in [draft #1535](https://github.com/apholmes7-bot/hiddenharbours/pull/1535), at `1e3fa3633dcdcc943e828c4dfe21e9623476f9e6`. Those implementation drafts are described here, not merged into this documentation-only branch. The separate [v26 draft #1516](https://github.com/apholmes7-bot/hiddenharbours/pull/1516) is an upcoming compatibility boundary, not part of this base.

**Demo distribution remains blocked.** The corrected configuration refuses both development and release demo packaging before setup because the single-island scene list omits the required sea opening without supplying an authored island replacement. Save isolation and the ending decision do not resolve that opening. The intended first week stays on St Peters; the route to Nine Mile Creek opens afterward through the weather/story progression.

## Where the demo save lives, and how the full game finds it

On pinned main, [`SaveStore`](../../Assets/_Project/Code/Core/Save/SaveStore.cs) defines `DefaultFileName = "savegame.json"` beneath `Application.persistentDataPath`. In the corrected #1510 implementation, `DefaultPath` applies `PathForMode` using `DemoBuild.Enabled`: full mode retains that exact path, and demo mode selects the same filename inside its `demo` subfolder. `ActivePath` applies the same mode selection to an editor test redirect. That redirect compiles out of players. No fallback, enumeration or automatic import opens the other slot.

[`PlayerBuild`](../../Assets/_Project/Code/Tools/Editor/PlayerBuild.cs) supplies the company/product identity for the persistent-data root. The corrected #1510 `-Demo` / `-buildDemo` entry points now fail immediately with the opening prerequisite. The underlying opt-in configuration still defines the island scene list and `DEMO_BUILD`, but no demo package is produced by those entry points. The separate output-package directory is independent of the separate save subfolder; changing the package location alone never isolated saves.

| Actual build situation | Does the full game automatically discover the demo file? |
| --- | --- |
| Same platform/user profile and persistent-data identity, corrected demo mode selected | No. The demo selects `demo/savegame.json`; full mode selects `savegame.json`. |
| Product argument or company identity changed between builds | No cross-identity discovery exists. Any future importer must deliberately locate and validate a source. |
| Different package output directories or executable copied elsewhere, unchanged identity | The package location does not decide save policy; the corrected mode selects the subfolder. |
| An editor/test save compared with a packaged player | Not a packaged carry-over proof. The editor redirect also honors mode isolation, but the release identity and real lifecycle still need verification. |
| Separate user profile, machine or platform | No transfer/synchronization is implemented. A supported transfer would be explicit. |
| An old experimental build using the original shared slot | It has no durable demo-origin marker. Do not treat that file as an import source without an explicit legacy policy. |

[`SaveService.Awake`](../../Assets/_Project/Code/Core/Save/SaveService.cs) opens `SaveStore.ActivePath` before the initial scene objects use the save and keeps that chosen path for later writes. `Open` calls `SaveStore.Read`, then deserialization and migration. A readable selected file becomes `Current`, with `LoadedExistingSave = true`; a missing or unreadable selected file produces a fresh blob even if the other mode has a valid save. [`ShellFlow.ContinueGame`](../../Assets/_Project/Code/Core/Shell/ShellFlow.cs) applies that loaded blob through `SaveRestore.ApplyToLiveServices` and publishes `GameLoaded`. Continue offers the selected slot only; there is no import choice.

The title does not overwrite a loaded game with boot defaults: `SaveService.WritesAllowed` blocks ordinary writes at the title. **New Game is different:** `BeginNewGame` keeps the selected file, creates a fresh blob and writes it immediately. `SaveStore.KeepReplaced` retains three rolling copies beside that selected file, named `savegame.kept-1.json` through `savegame.kept-3.json`; the demo copies therefore remain inside `demo`. It also protects the first overwrite of an unreadable selected save. Ordinary saves replace the selected file atomically through a sibling `.tmp`; they do **not** create a kept copy every time. No save schema or field changes are required for this directory separation.

## Which facts carry, and which ones need care

The file contains data and stable identifiers, not scenes, sprites or a list of build-enabled regions. A full build with the same island content and identifiers can read those saved facts even though it includes additional regions. Adding a region to a build does not require inventing progress there. Conversely, a file being readable does not prove every live object has a working restore consumer.

| Existing field or state | Interpretation in the full game and the present limit |
| --- | --- |
| `SchemaVersion` | The migration version, currently 25. It is not a demo/full-game marker. See the newer-version hazard below. |
| `GameTimeSeconds`, `DayIndex`, `WorldSeed` | The week keeps its time and stored seed; no reset to day one is needed. `SaveRestore` seeks the live clock. However, `EnvironmentService.WorldSeed` reads its serialized `_worldSeed`, and the inspected restore path does not set it from `SaveData.WorldSeed`. Identical authored seeds hide this gap. A changed seed between releases needs a restore fix or an explicit supported-seed policy before promising identical weather. The next snapshot also copies the live environment's seed back into the save. |
| `Money`, `OwnedLicenses`, `OwnedBoats`, `RepairedBoats`, `ActiveHullId`, `OwnedGear` | These are ordinary earned progress, not demo unlock tokens. Carry them intact. Full-game content must retain the same licence, hull and gear ids. `OwnedFleet.RestoreFromSave` looks up `ActiveHullId`; an unknown hull is a no-op, not a migration or a visible import error. |
| `OnboardingFlags`, whose rows have `Key` and `Value` | Includes story progress and, when an author sets it, `st_peters.weather_turned`. `SaveService.SetFlag` uses the existing generic list. No producer of that particular key exists on the pinned base. A full-game weather/barrier consumer must actually use the agreed key; copying the file cannot supply missing story content. |
| `BoatHoldCatch`, `BucketCatch`, `FreezerCatch`, `BaitStock`, `PotStock`, `TubStock`, `SupplyStock` | Existing catch and counted supplies can carry in their current serialized representation. Keep quantities and freshness state; an import should not convert everything into money or grant replacement goods. This says nothing about later systems that have not yet written their own state. |
| `StoredContainers`, with `StoredContainerDto.Key`, `ContainerDefId`, `Items` and `Catch`; `StoredItemDto.ItemId`, `InstanceId`, `Count` | The v25 storage memory depends on stable container and world-instance ids as well as Def ids. Full-game island content must keep those ids and placements compatible, or provide an explicit mapping. Reading a row does not authorize moving its goods to another container. |
| `KitchenStores`, `CookJobs`, `CaughtSpecies`, `NpcGiftDays`, `PlayerNotes` | Already represented data can remain intact. The demo configuration does not fork these types. Per-day rules still use the carried game time; import should not manufacture a fresh day. |
| `PlayerRecipe`, `PlayerName`, `WornOutfitId`, `PlayerTraits`, `PlayerNeeds`, `PlayerBody`, `PlayerCleanliness` | Keep identity and current condition. Referenced appearance/content ids must still resolve. The import is continuation of the same player, not a second character-creation pass. |
| `RestRegion`, `RestPosX`, `RestPosY`, `RestLevel`, `RestBedId`, `RestWokeAtSeconds` | These say where and when he last slept. Full builds currently also begin in St Peters. A valid same-region land-bed anchor can be applied by `RestWakeRestorer`; this is the cleanest intended handoff. A changed island layout can make old coordinates unsuitable even when the region id is unchanged. |
| `RestAboard`, `RestBoatHullId`, `RestBoatRegion`, `RestBoatPosX`, `RestBoatPosY`, `RestBoatRotation` | An aboard sleep is recorded, but `RestWakeRestorer` does not currently place and board the saved boat on load. It requests `SleepPlaceWakeRequested`, warns and keeps the authored spawn instead. Recording these fields is not proof of an aboard continuation. |
| Region identifiers in `PlacedTraps`, `PlacedLonglines`, `NavWaypoints`, `NavRoute`, `NavTrack` and other scoped rows | A legitimate island week can remain scoped to the island. Additional full-game scenes do not reinterpret island ids. A manual reverse copy remains unsafe: a full-game save can name an omitted region. Normal mode isolation prevents this accidental discovery, but an unsupported manual copy cannot make the missing region loadable. |
| `DemoBuild.Enabled`, `DemoEnded`, `DemoEndingSnapshot.Ended`, `ISaveService.CompletedWrites` from the drafts | Build configuration, transient notification and session-only state. None is a `SaveData` field or a persisted end flag. There is no saved “demo mode” for the full game to misread. |

The region limit in #1510 and its #1504 prerequisite is a runtime/build-availability check. It does not purge saved rows for unavailable places. In the other direction, [`RestWakeRestorer`](../../Assets/_Project/Code/Core/Save/RestWakeRestorer.cs) currently declines a saved land anchor outside the booted region, emits `SleepPlaceWakeRequested`, warns and retains the anchor. Simply launching the full game with an older or unusual demo file is therefore not a complete region-relocation implementation.

The first-week route must remain honest: if the final saved bed is on St Peters, carry him into that bed/region and let the full game's story open the way onward. Moving him and all his belongings directly to Nine Mile Creek would be a new progression and transport rule, not a save conversion.

## The end flag and version are separate questions

**There is no durable “demo ended” flag in these changes.** The weather flag is an ordinary `OnboardingFlags` entry and should survive carry-over; clearing it would close the route he earned. `DemoEnded` is an event, not a flag. The #1535 proposal emits it only in demo mode after a qualifying saved sleep. The full-game configuration disables that decision, so carrying the weather flag does not cause a full-game ending.

The completion snapshot lasts only for the live save object unless a caller explicitly carries it in memory. After a fresh-process load, v25 data cannot distinguish a weather flag saved before the final sleep from a demo whose ending was already presented. `RestWokeAtSeconds` has no matching flag-set timestamp. The proposal therefore emits nothing on load but may emit again after the next qualifying demo sleep. That limitation does not prevent full-game carry-over, because the full game does not run the ending decision. Persisting presentation completion would be a separate approved saved fact and migration/default policy; this document adds none.

**v25 to v25 is the current common format; older to newer is the intended migration direction.** [`SaveMigration`](../../Assets/_Project/Code/Core/Save/SaveMigration.cs) has incremental steps and repairs absent/null containers. The v25 step supplies storage state for older files. #1516 proposes v26 and additional data, including shopping-related rows; that branch must be verified separately before it is called a release-compatible reader. No v26 fields or migrations are copied here.

**Newer to older is not safely rejected today.** At the end of `SaveMigration.Migrate`, a `SchemaVersion` above `CurrentVersion` is assigned `CurrentVersion`. The older `SaveData` type cannot represent newer fields. A later save from that older build can therefore lose those fields while retaining a seemingly valid version number. The corrected demo no longer discovers the full-game file automatically. A manual reverse copy or an importer without a version gate could still expose a newer file to an older reader, which could overwrite it without a kept backup on an ordinary save. The existing atomic write prevents partial files; it does not prevent this semantic downgrade.

An import gate should inspect the source's declared version **before** passing it to this migrator, reject unsupported future versions without writing either file, and preserve the source bytes. A schema number alone also does not certify that all content ids still resolve. This is a proposed validation step, not current behavior.

## Options against the code that exists

| Option | What the player experiences | Cost and consequence in this code |
| --- | --- | --- |
| **Same file** | Both executables would continue one shared playthrough. | **Rejected direction:** it would undo the implemented isolation. New Game in either executable would replace the shared slot, and an older reader could rewrite a newer save. Three kept copies do not isolate the playthroughs. There is no durable origin marker. |
| **Separate demo file, explicit full-game import** | The full game offers to carry a saved island week, and he can keep an existing full-game playthrough instead. The demo source survives the copy. | **Moderate remaining work:** retain the implemented `demo/savegame.json` destination, add explicit discovery, validation and an import choice, preserve an existing target through `KeepReplaced`, write the validated copy atomically, then open/restore it through the ordinary lifecycle. Do not call `BeginNewGame`, which replaces progress with defaults. `SaveService.Open` is internal; there is no import coordinator or UI. No gameplay schema field is required merely to copy a compatible file. Reject future versions and incompatible content before migration. |
| **No carry-over** | The full game uses its own existing slot or starts a fresh playthrough; the demo week stays separate. | **No importer cost, largest player cost:** this is the current discovery behavior after the configuration correction. A release must state the policy clearly. Preserve both files. This does not solve restoration gaps in either build. |

The implemented subfolder under the existing identity makes each slot unambiguous without changing branding. Any future import must explicitly select the source and target; it must not turn normal loading into cross-slot discovery. If previously distributed builds used the shared filename, a legacy discovery policy is still required: v25 cannot prove demo origin. No assumption that such distribution occurred is made here.

The existing save tests provide useful pieces: `SaveServiceTests` and `SaveRoundTripRegressionTests` cover data/migration, `SaveNeverClobberedTests` covers title/replacement safety and, in corrected #1510, both directions of slot isolation, saving and exact backup rotation with the opposite files locked, and `SaveDeferredWritesTests` covers write grouping. `SaveRestoreTests` and `SaveLoadRestorePlayTests` cover restore consumers, with the latter explicitly constructing its environment from the reloaded seed. None is a shipped demo-to-full import test. A release proof should use two built players under the intended identity, a normal island bed save, stable inventory/storage ids, the same seed, and a newer-version rejection case. Document links and 48 existing fields were checked against pinned main. No player, full test suite, live save, migration or actual demo-to-full import was run for this document.

## Questions only the owner can settle

1. **Should a saved demo week carry into the full game?** Lean: yes, through an explicit copy/import choice with separate files. Keep the work he has already done while protecting any existing full-game playthrough.
2. **Must he finish the demo before he can carry it over?** Lean: allow any valid saved island progress, including an unfinished week. There is no durable completion fact to enforce a finish requirement, and being interrupted should not erase earned progress.
3. **What happens if a full-game save already exists?** Lean: keep it unless the player explicitly chooses replacement; preserve it through the existing kept-copy mechanism and leave the demo source untouched. Do not select by filesystem modification time or merge economies and inventories.
4. **Can the old demo reopen progress written by the full game?** Lean: no supported reverse transfer. Use separate destinations and reject newer source versions before migration; never silently downgrade them.
5. **Where does a carried week resume, especially after an aboard sleep or a changed island layout?** Lean: keep the same compatible St Peters land-bed anchor. Make aboard/cross-region restoration and any coordinate mapping explicit release work before promising those cases; do not transport the player or goods to the next region as an import shortcut.
6. **Does “the week is kept” promise the same world seed and conditions across releases, and must the ending stay dismissed after relaunch?** Lean: preserve the seed and verify its live restoration; keep the ending disabled in the full game. Persistent demo presentation completion can be approved separately, with a decision for a crash between the final save and the ending being shown.
