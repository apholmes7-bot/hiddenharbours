# Island demo ending decision (proposal)

The demo ends after the player's first actual sleep whose bedtime follows `st_peters.weather_turned`, once that sleep's save write has completed. The full game never raises the ending. This is a session-only decision and a listener seam; it adds no screen, scene, travel refusal or saved completion field.

`DemoEnding` is a plain Core class. It marks its state before publishing the existing `DemoEnded` event, so a reentrant listener cannot publish the ending twice. A presentation can subscribe to that event and resolve the single key `demo.island_week_complete` (`DemoEnding.TextKey`). There is no text value or presentation listener here, and no automatic quit, pause, scene load or freeze. With no listener, play continues after the signal.

Both existing sleep paths are connected. `SleepFlow.Confirm` samples the flag at the start of a chosen sleep. `RestSaveResponder.Fulfil` samples it before its instant sleep advances the clock. They finish the decision after waking, after the write, after the normal save outcome, and after the instant path releases its cover. A flag first set during sleep waits for the following sleep. Choosing a duration, declining, cancelling without advancing time, a held clock, or an ordinary autosave cannot end the demo. Waking early after actual time asleep can: that is already a completed sleep under the sleep/save contract.

The write needs a receipt. `LoadedExistingSave` means a save exists, so it can stay true when a later write is refused or deferred. The additive `ISaveService.CompletedWrites` property counts successful synchronous `Save` writes in memory. `SaveService` advances it only after `SaveStore.Write` returns. The default for other implementations is zero, so an implementation that provides no receipts cannot accidentally end a demo. The ending compares the count immediately around the sleep write, and also checks that the same save service and blob are still active. No receipt, no ending. A thrown, refused or deferred write leaves the next successfully saved sleep eligible. A later deferred flush alone does not publish an ending; the current production sleep paths do not wrap their writes in a deferral scope.

`DemoEndingSession` keeps one decision per live `SaveData` object through weak references. Continuing the same in-memory game preserves completion. A new game has a different blob and gets a fresh decision. The public `Capture` and `Restore` methods expose a plain `DemoEndingSnapshot`, whose only fact is `Ended`; restoring it is silent. A supplied snapshot can preserve the decision when a caller replaces a blob during the same session.

A **v25 file by itself cannot say the ending was shown**. The weather flag may have been saved before the qualifying sleep, and `RestWokeAtSeconds` does not record when that flag changed. Inferring completion from those fields would skip legitimate endings. Consequently a fresh process loading a completed demo file publishes nothing on load, but can end again on its next qualifying saved sleep. This limit is deliberate under the no-save-change scope.

A future persistent version needs an approved durable completion fact, its default/migration policy for existing saves, capture in the successful wake write, and restoration before the ending becomes eligible. It must decide whether a crash after that write but before presentation counts as shown or pending. It must also define what the full game does with the fact. It must not serialize receipt counters, weak references or in-progress sleep tickets. No such field, flag row, schema change or migration is added here.

The existing decision/configuration search found `DemoBuild` and the reserved `DemoEnded` signal; both are reused. The existing sleep and write fixtures are `SleepFlowTests` and `SaveDeferredWritesTests`. The former belongs to the prerequisite draft and is left intact; the latter is extended to pin receipts for success, refusal and failure. `DemoEndingTests` adds the ending cases, both runtime modes, both sleep paths, same-session Continue, snapshot restoration, v25-only reload, new games, failure, early wake and reentrancy.

The standalone decision source and shared event code passed 13 probes with substitute save and engine interfaces. That is limited logic proof. Unity, the complete assembly, EditMode execution, disk-backed receipt cases and the player were not run locally; CI must compile and run them. No existing save, config asset, art asset or scene was changed. This proposal depends on the opt-in demo configuration in draft #1510 and includes that prerequisite unchanged except the event's now-current summary.
