# Content validation coverage and gaps

Audit of `f1b4ab2f59f417eda06f2239f7dee25d4c52ad23`. This is a source audit, not an EditMode execution report. Existing assets, appearance, configuration and save formats are unchanged. The aim is to protect the working coast (P3) from broken content additions.

## Candidate rules

Test paths below are relative to `Assets/Tests/EditMode/`. “Covered” describes the stated scope, not every possible serialized field.

| Rule | What main checks today | Remaining gap / safe next step |
|---|---|---|
| ID format | `DefIdentityContractTests` requires nonblank `Id` or `Spec.Id`. Individual suites enforce shapes for recipes, foods, crops, produce, plots, deck gear, held props, water, breaker sites, traits and others; some only check a prefix. | No common strict `type.snake_case` rule for every discovered identity. Baseline plus additions contain 2,412 rows across 173 declared types; 66 IDs fail a single-dot, lower-case snake-case rule. Preserve those stable IDs in an exact named exception list; reject new departures. |
| Unique IDs across all Defs | `DefIdentityContractTests` reflects concrete project ScriptableObjects whose names end in `Def`, plus `InstrumentOffer`; requires uniqueness within type and exactly 16 cross-type shared plant IDs, each belonging only to `PlantSpeciesDef` and `ShorePlantDef`. `ContentValidationTests.DefIds_AreGloballyUnique_AcrossAllDefTypes` itself covers only fish, hull, region, trap, bait, water and plume. | Already covered within the reflected inventory. Do not introduce a competing blanket uniqueness rule that rejects the approved plant pairs. Non-Def offers other than `InstrumentOffer` are outside that reflection selector. |
| Prefix matches class | Domain suites pin some prefixes, e.g. `fish` is the semantic prefix of `FishSpeciesDef`, not its lower-cased class name; both plant classes intentionally use `shoreplant`. `BirdHauntContentTests` distinguishes roost and haunt prefixes by kind. | No common type-to-prefix policy. Record explicit established prefixes, including semantic aliases; fail unclassified new types. Do not derive permission from newly appended ledger rows at test time. |
| Every Def reference resolves | `ContentValidationTests` resolves fish regions, region fish, bait fish, trap bait/catches, village links, key-scene regions/pieces, breaker regions and plume water types. Dedicated bite, NPC, conversation, quest, farming, food, relationship, deck-work and supply suites add their own typed edges. | No universal scan of serialized object references or string-reference schema. A GUID existing alone does not prove its local file ID or expected type. Extend the loaded-asset harness for typed object links and explicit uncovered string edges; do not treat all `*Id` fields as Def references (flags, anchors, station tokens and instance IDs are different domains). |
| Prices strictly positive | Fish `BaseValue`, licence fees and gear prices are checked **nonnegative**. Supplies and bait prices, pot offers and the named wholesaler stock are **positive**. The damaged dory's repair cost is positive; its purchase price is nonnegative. | No common all-price rule; zero is permitted by several existing contracts. Record that distinction instead of silently changing economics. Positive fish base values and minimum weights are additional checks that can be separately proposed with exact exceptions if needed. |
| Weights strictly positive | Fish: `MinWeightKg <= MaxWeightKg` and `MaxWeightKg > 0`; island goods and research containers check their specific positive dimensions/mass through their own validators. | Fish minimum weight may still be zero or negative; no shared finite-number rule. Add finite, positive endpoints without changing authored weights. Do not apply positivity indiscriminately to optional capacities or normalized weights. |
| Stack sizes strictly positive | Bait lots are at least one; deck stack capacities match the rig's explicit numbers; research tubs have `MaxStackCount == 1`; research data pass their model validators. | No common stack-size field exists across Defs. Zero can mean a surface is unavailable. Keep typed rules rather than reflecting any field containing “stack” and demanding positivity. |
| No two files define one entity; one entity per file | Within-type uniqueness and the GUID/type/ID ledger bind each registered entity to one file GUID. Deck gear and boat-owner suites explicitly inspect assets within files. | General discovery loads one asset per path and can miss an additional Def subasset. Add a file-shape check over all discovered Def asset paths, including different-type subassets. Different IDs for semantically identical entities cannot be inferred from text. |
| Sale goods have a buyer | `FoodContentValidationTests.ShopFoods_AreOnACounter` checks supply food **sellers**; `StoreClerkContentTests` checks stocked browse rows, mutually exclusive browse/sell rows and payout wording; market and counter tests exercise actual catch sales. `WholesalerStockTests` resolves named sellers and offers. | There is no shipped universal `BuyerDef` registry or “sale good” flag; the architectural buyer entry is a plan. A seller is not a buyer. Universal buyer coverage needs an explicit domain contract; do not invent a later-phase buyer system in a test PR. Existing catalog seller IDs can be checked against `SellerDef` independently. |
| Recipe inputs/outputs exist | `Food/RecipeContentValidationTests` checks unique recipe and output IDs, station/output shapes, known input kinds, positive work time and Resources location; prep species exist, categories are defined, item inputs name food items/supplies, cooktop inputs have reachable prep feeders. Food forms resolve outputs. `Food/CookingStationContentTests` requires edible cooktop outputs and microwave input/output food metadata. | Species/category/intermediate checks are partly station-specific. An unfamiliar but well-formed station can escape those input checks. Check input kind resolution independently of station and require a shipped cooking station accepting every recipe station. Outputs are minted by recipes: prep outputs need not have edible FoodDefs. Do not require a second entity for every intermediate. |
| Stable / retired IDs | The identity ledger preserves every GUID/type/ID, requires additions to be registered and requires type coverage. Its reader rejects malformed rows, repeated JSON fields, duplicate GUIDs, duplicate type/ID pairs and undeclared types. The retired-ID sweep in `ContentValidationTests` covers fish, hulls, regions, traps and bait; held props also check retirement. | Frozen baseline must never be appended. New registrations belong in addition files. Retirement checks are not universal across all reflected types. |
| Authored YAML survives loading | `ContentValidationTests.AuthoredAssetText_EscapesEveryApostrophe_SoNoLineIsSilentlyTruncated` scans `.asset` files under Data for improperly closed single-quoted scalars, including multiline strings. | It is a targeted quote check, not a YAML parser or universal missing-script/GUID validator. |

## Implementation boundaries

Extend existing test suites rather than replacing them. Reuse the public type selector in `DefIdentityContractTests`; that file is also touched by open PR 1232, so additions should live in the available `ContentValidationTests` harness. Recipe changes belong in `Food/RecipeContentValidationTests`. Keep all exception lists test-only and exact (type, GUID and ID where applicable); fail stale entries so a fix removes its exception. Never normalize IDs in assets or modify the frozen identity ledger.

The 66 format departures are: 23 route IDs, 16 light IDs, nine lot IDs, nine yard IDs, three commons IDs, three relationship IDs, two conversation IDs and one beach ID. This count comes from the committed ledger plus additions, not a Unity import. The related identity suite remains responsible for proving the inventory matches loaded assets.

No editor lease was granted for this audit. Native type discovery, imports, scene wiring and the EditMode pass remain unverified here. Text and source inspection cannot establish buyer reachability or visual correctness.
