# A saved purchase ledger for the island store

Save what the player took from the store, then rebuild the shelves from the same calendar and those purchases when the game loads. A purchase must survive a reload until its effect has been erased by a full delivery. Save five facts per purchase group: shop, shelf line, quantity in the good's units, game day and exact game seconds. Do not save shelf counts, tide, deliveries or villagers' consumption.

This is a plan for the later island-memory slice, whose version 26 change is approved for that slice only. This document changes no runtime, save format, data or appearance. It serves P3, the living coast, and P4, goods earned and handled by hand. Recording a purchase does not carry an item to a boat or storage container.

## Smallest saved row

Proposed future Core DTO: `StorePurchaseRowDto`, in `Assets/_Project/Code/Core/Save/SaveRowsV26.cs`, with a single new `List<StorePurchaseRowDto> EconomyLedgerRows` on `SaveData`. Both names are proposed, not existing APIs. The list name follows the living-economy plan; here its meaning is explicitly **island shelf purchases**. Its older four-field sketch, `{ LedgerId, KeyId, Units, SettledThroughDay }`, cannot retain the time-of-day boundary used by today's shelves. Do not treat a settlement watermark as a purchase day or reuse these rows for generic stock snapshots or market sales.

| Field | Type | Meaning and invariant |
|---|---|---|
| `ShopId` | `string` | Stable `ShopDef` id, e.g. `shop.st_peters_general`; nonempty, ordinal comparison. |
| `ShelfLineId` | `string` | Stable line id, e.g. `line.gas_jerry_can`; nonempty, unique within that shop. Never an array index or display name. |
| `Units` | `double` | Positive finite quantity removed, in the mapped good's units (kg or litres according to its Def), **not** item count. Capture the actual amount at purchase; do not multiply by a potentially retuned item size on load. |
| `Day` | `int` | Nonnegative purchase day, equal to `floor(Seconds / SecondsPerDay)` using the same clock configuration as the shelf. |
| `Seconds` | `double` | Finite, nonnegative **absolute game seconds**, at the precision of `IGameClock.TotalSeconds`; not wall time, seconds within a day, or rounded hours. No later than the save's `GameTimeSeconds`. |

The root already stores `WorldSeed` and `GameTimeSeconds` ([SaveData.cs, lines 21–36](../../Assets/_Project/Code/Core/Save/SaveData.cs#L21-L36)); do not repeat them in every row. Day is derivable but retained to match the draw/ledger day contract and detect inconsistent input. Resolve the good from `(ShopId, ShelfLineId)` on load; runtime good indexes never escape into the file. No price, wallet balance, item destination, delivery receipt, player id or cached remaining stock belongs here.

Example: buying one gas can writes 20 units at `(shop.st_peters_general, line.gas_jerry_can, day, exactSeconds)`. Another successful can purchase at precisely that instant makes 40 units. Buying at a later instant creates another row, even on the same day. The actual numeric timestamp comes from the clock, not from this example.

## Recording and folding

1. The future counter checks stock, price and the physical receiving destination. Only a successful committed purchase updates the row list. A failed purchase changes neither rows, wallet nor destination. The purchase-row append and shelf debit describe the **same** mutation; they are not two independent decrements.
2. Mutate the current save's rows in memory through a Core-facing seam, following the [StoredContainers.cs, lines 16–23](../../Assets/_Project/Code/Core/Save/StoredContainers.cs#L16-L23) pattern. Economy interprets the rows; Core owns the DTO, not an Economy dependency. App supplies the calendar and composition. Rebind when `SaveService.Current` changes; no static list shared between worlds or saves.
3. Fold rows only when **shop, line, day and exact seconds all match**, summing units in accepted transaction order. Do this during the live mutation as well as restore normalization, not just on serialization. Do not fold different instants into a daily sum: that would make a purchase affect an earlier query on its day. Do not drop an identical row as a duplicate request: two genuine purchases in one tick are legitimate.
4. Keep canonical ordering `(Day, Seconds, ShopId ordinal, ShelfLineId ordinal)` for serialization and replay. Use the same aggregation and summation order live and after load. Never use dictionary iteration order as arithmetic order. Reject a new purchase if its amount or aggregate would be nonfinite; never wrap or silently cap a valid purchase history.
5. Request persistence only after the transaction's effects are complete. Existing `ISaveService.DeferWrites()` / [SaveService.cs, lines 146–177](../../Assets/_Project/Code/Core/Save/SaveService.cs#L146-L177) can postpone nested save calls. This scope is **not a rollback transaction**: validate before mutation, and explicitly undo effects if the future purchase path can still fail. Keep the title and mid-sleep write gates. Save the clock, money, delivered ownership and purchase rows at one consistent instant.

Folding is additive accounting, not network deduplication. The row intentionally has no request id; that distinction matters for co-op below.

## When rows clear

A scheduled run, a successful crossing, one full-looking shelf, or the passage of midnight is insufficient. [IslandStoreLedger.Step, lines 187–218](../../Assets/_Project/Code/Economy/Island/IslandStoreLedger.cs#L187-L218) computes one shared capacity scale. A gas purchase can increase the requested load enough to reduce another good's delivery. Therefore pruning is by a recovered **back room**, not independently by purchased line.

The conservative rule is to remove a prefix of purchases only after a later run fully tops up the affected ledger and replay with and without that prefix agrees exactly on the **whole vector of morning levels**. Check after delivery and before that day's use and purchases. The existing full-top-up branch assigns the exact target, avoiding approximate equality. If a seasonal target changed, a zero-want good remains above target, or capacity constrained any required recovery, do not infer equality from the run flag; compare the states and keep the rows unless recovery is proven.

For a qualifying recovery on day `R`, only rows with `Day < R` can clear. Purchases on `R` happen after the model's morning delivery, including purchases at second zero; retain them. Rows for other shops/ledgers are unaffected. If stores ever share one ledger, all of their rows must participate in the comparison; independent shelf instances cannot each overwrite its `ExtraDraw` callback.

Compact a snapshot at a deterministic save/load settlement boundary, not as a side effect of arbitrary `CountAt` order. Compare the original and compacted replay at the saved instant and subsequent days. A compacted file promises continuation from that instant, not reconstruction of purchases before its erased prefix. Keep earlier-time queries against retained session history valid; do not erase live history merely because a save snapshot was compacted. The existing test that queries before a purchase must still pass.

**Lookback is an unresolved correctness gate, not a recovery certificate.** Today `Settle` starts at `max(0, day - LookbackDays)` from full ([IslandStoreLedger.cs, lines 164–169](../../Assets/_Project/Code/Economy/Island/IslandStoreLedger.cs#L164-L169)); `TryTakeOne` also drops older rows on a later successful purchase ([IslandStoreShelves.cs, lines 135–139](../../Assets/_Project/Code/Economy/Island/IslandStoreShelves.cs#L135-L139)). Neither checks for a full top-up. Merely saving those session rows would preserve this expiry, not prove durable recovery.

For the later slice, retain unproven rows and use a reference replay from day zero to test recovery and the bounded optimization. If the normal window excludes an unrecovered purchase, extend replay to cover its history rather than silently refilling the shelf; retaining an ignored row alone is no fix. A day-zero reference can reconstruct from the remaining rows after a proven prefix recovery, because both histories meet at the same state there. Require no-purchase parity with the existing model over the supported content, plus purchase-heavy, capacity-limited and winter cases. If the bounded model disagrees, resolve the replay contract before shipping persistence; this document does not authorize a balance or configuration change to make that proof pass. No fixed maximum row count or guaranteed recovery time has been established.

## Replay on load

1. Follow `SaveStore.Read` → `SaveSerialization.FromJson` → `SaveMigration.Migrate`. Preserve the loaded rows before any scene or temporary default service can write them away. The existing shell restores scalar state before releasing the clock ([ShellFlow.cs, lines 115–131](../../Assets/_Project/Code/Core/Shell/ShellFlow.cs#L115-L131)).
2. At the saved seed and exact time, resolve the shop and line Defs, construct the same ledger, run-calendar and winter inputs, and import valid rows **before the first shelf settlement or purchase**. Construct one owning service per ledger. Add an explicit restore seam later; do not call `TryTakeOne` to import history, since that rechecks old availability, appends again and can prune history.
3. Validate `Day` against `Seconds` with the configured day length at composition, where that value is available. Migration stays asset-free. Rows with unknown nonempty ids are preserved in the save and reported unresolved, never remapped to another line or charged again. Inconsistent or future timestamps must not be applied or used to prove compaction; preserve them for diagnosis rather than making up a new purchase time.
4. Replace the shelf's imported draw set; never append it on each `GameLoaded`. Invalidate `_settledDay` / `_settledVersion` and warm once at the restored time. Earlier days' units enter `ExtraDraw(good, day)`. Today's shelf uses morning stock minus elapsed island use minus rows on that day with `Seconds <= savedTime`. Do not additionally subtract a saved final balance. The ledger's dusk aggregate and the shelf's timed subtraction are two views of the same draws, not two charges.
5. Rebuild services from the currently selected save on restart, region re-entry and New Game. An empty row list means the calendar-only shelves. Repeated restore and repeated reads must be inert. Publish/read readiness only once rows and scalar state are available; do not rely on unspecified subscriber ordering during `GameLoaded` ([SaveRestore.cs, lines 42–65](../../Assets/_Project/Code/Core/Save/SaveRestore.cs#L42-L65)).

The invariant is: identical seed, time, Def/config inputs and accepted canonical rows yield identical shelf counts and back-room levels before save and after reconstruction, regardless of polling frequency or visited days. The seed reaches this model through supplied calendar inputs; the shelf constructor does not itself accept a seed.

## Determinism risks and what remains unconfirmed

| Risk | Decision or outstanding proof |
|---|---|
| Two purchases in one tick | Sequentially accept against current stock, fold only successful debits, and pin exact units and wallet/destination effects. A list is not an idempotency key. Arbitrary fractional item sizes can expose floating-point grouping differences; live and loaded paths must use the same canonical arithmetic and pass exact round trips. |
| Load mid supply run | The present calendar answers only a day-level boolean; `Step` applies delivery in the morning, with no travel/arrival state ([IslandRunCalendar.cs, lines 20–29](../../Assets/_Project/Code/Economy/Island/IslandRunCalendar.cs#L20-L29)). Preserve that model on load. There is no verified instant of physical unloading to use for clearing. A later physical-run slice must settle arrival ordering before changing this rule; the purchase list cannot stand in for cargo or delivery progress. |
| Calendar horizon and season | `DaylightRunDays` returns false outside its prepared range ([IslandRunCalendar.cs, lines 33–53](../../Assets/_Project/Code/Economy/Island/IslandRunCalendar.cs#L33-L53)). Composition must cover the complete replay range, cadence lookback and tide-window margins with the same seed/config and winter function. A short range on load changes deliveries. Production composition is absent, so this is not verified. |
| Lookback and pruning | Existing tests show bounded examples, not guaranteed full recovery under all purchases or seasons. The replay extension, recovery comparison, runtime cost and maximum history size remain to be implemented and measured. Do not use a cosmetic full shelf or elapsed days as proof. |
| Changed content | Stored units survive item-size retuning, but changing the good behind a line id, its unit, clock day length or calendar balance can change history. No content-version replay compatibility contract was found. Keep stable mappings; any such future change needs an explicit compatibility decision, not silent reinterpretation. |
| Save/load transaction | No shelf purchase transaction or import/export API exists. The Core stock contract only debits stock. Atomic file replacement does not prove wallet, physical item delivery and rows are committed together in memory. This requires counter integration tests later. |
| Co-op later | Treat stock and rows as world-owned, written by one authoritative host; player inventories remain separate. The host orders simultaneous requests and checks the last item once. Durable retry deduplication, disconnect rollback and player attribution require a future command/receipt contract; five aggregate fields cannot provide them. Do not add networking, player ids or random transaction ids in this slice. |
| Historical reads | Clearing is valid for continuation after recovery, not arbitrary rewind to a removed purchase. Preserve retained session-history queries and test snapshot compaction independently. No general time-travel save contract was found. |

This work is source inspection and design only. No Unity editor, EditMode/PlayMode tests, live purchase, saved game, visual comparison or performance measurement was run. The later slice is complete only when the migration, exact reconstruction, full-top-up clearing and integration cases above pass, with the remaining replay and transaction questions resolved in code.
