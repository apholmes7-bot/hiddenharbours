# Demo with a friend: completion checklist

The demo is the first week on St Peters for **two to four players**. It ends when Ginny completes her evening word. Progress through that word must be committed to the demo's own file before the closing card and return to title. Relaunch restores the ended state without replaying the card. A saved sleep is not an ending trigger.

This is a source checklist, not a claim that multiplayer or the ending is implemented. It changes no code, save format, scene or appearance. The host-world policy below is a recommendation that makes responsibilities concrete; the accepted decisions are the participant count, evening ending and separate demo save. Persisting participant records still needs its own approved representation. Personal state must be per participant, even when there is only one connected player.

## Ownership to implement

Recommended policy: one host-owned demo world, a shared purse, and stable participant ids for two to four people. Shared story milestones can be contributed by any admitted participant, with actor provenance and that actor's permissions checked. A world milestone does not grant personal licences, tutorial acknowledgments or belongings to everyone. Ginny's validated word commits the world ending once; every connected participant receives the word and the closing beat. The participants do not each have to repeat the same world-ending conversation.

Freeze the recipient roster with the completion transaction. A join accepted before that boundary belongs to the roster; a join after it restores an ended world without replay. Track connected recipients' presentation locally per participant, independently of world completion. A disconnected recipient must not keep the commit or other clients' return to title waiting forever. Rejoining restores the committed ending silently. Never infer identity from a player name, array position, the local controller, the save object reference or the operating-system account.

## Commit, presentation and reconnect order

1. The host accepts one actor's completed word only after validating the authored conversation, evening window, admitted world and five gate facts. A cancelled line, stale conversation or unauthenticated participant cannot complete it.
2. The host captures the word progress, world completion and agreed participant state in the selected demo transaction. Existing version 26 has no roster; design that representation before implementing persistence. No new field or encoding is approved by this checklist.
3. Wait for the receipt for that transaction. Failure, refusal or deferral leaves presentation unissued. Retry uses the same completion identity so duplicate callbacks cannot duplicate effects. No guest, full-game file, temporary file or backup is used as an alternative destination.
4. After successful commit, publish the scoped completion and show each connected participant his closing card. Input focus and dismissal belong to that participant. Acknowledgments may coordinate shutdown, but do not create a second gameplay completion or rewrite someone else's character.
5. Return each client to its local title safely. Host shutdown cannot discard the committed world or use a guest's stale snapshot. Relaunch, reconnect, late join and a crash between commit and presentation all restore ended state without replay. A crash before a successful write resumes the preceding durable state and may legitimately reach the word again.

The demo remains island-only after completion. Restoring an ended state is not automatic permission to import into the full game, open mainland passage, teleport goods or merge inventories. Automatic transfer does not exist in #1510.

## Acceptance cases to add to existing fixtures

- [ ] Run the ending sequence with exactly 2, 3 and 4 distinct participant ids. A guest completes the word while the host is elsewhere; everyone in the committed roster receives the same completion, and each controls only his own card.
- [ ] Split contributions among players. Check actor-specific licence and catch provenance, one shared story result and purse, separate hands/needs/tutorial receipts, and no invented personal grants. Repeat with two unrelated worlds in the same process to detect static cross-talk.
- [ ] Repeat, delay and reorder the word callback, save receipt, completion message and dismissal. Assert one world completion and at most one card per connected participant; a stale-world message changes nothing.
- [ ] Inject a failed, refused and deferred final write, including an earlier successful unrelated save. Assert no card/title transition from that attempt; retry commits the intended demo transaction once.
- [ ] Crash before commit, after commit but before the card, during the card and after dismissal. Recreate services and deserialize new objects. Only the uncommitted case may reach the word again; all committed cases restore ended state without replay.
- [ ] Disconnect a guest before the roster boundary, during commit and after notification; reconnect under the same stable id. No duplicate character, rewards, ending or indefinite acknowledgment wait. Join after completion receives ended state without a replay.
- [ ] Lock each guest's independent demo and full-game slots, their temporary paths and kept copies. Host save, Continue, completion and New Game must leave them byte-identical. Repeat normal full/demo isolation in both directions using the existing locked-slot fixture.
- [ ] Quit a guest while another participant is reading the card. Only that guest detaches; the other's card remains usable. Close the host during the card and verify the committed world survives and every reconnect restores ended state.
- [ ] Day rollover, weather changes, autosaves, a completed sleep and one participant's local UI callback cannot end the demo before the authoritative word. Full-game mode never emits the demo completion.
- [ ] Retain omitted-destination refusal on all peers and reject mismatched demo/full builds before admission. No client opens the mainland from a local flag; demo packaging remains blocked until the authored island opening is verified.

No Unity, test suite, network session, player build, live save or visual check ran for this checklist. Source links and their line anchors were checked against the pinned commits. Existing tests are references for future extension, not evidence that these multiplayer cases already pass.
