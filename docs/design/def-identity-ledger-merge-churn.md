# Def identity ledger: reducing merge churn

**PROPOSAL, nobody has accepted this.** Decision for the owner and lead architect. This document changes no test, fixture, tooling, asset or save format.

## Problem and evidence

Independent content additions currently edit the tail of one JSON file. A clean content merge can therefore make another tested PR conflict, requiring another branch refresh and CI run. The integration audit already identified [nine PRs sharing the ledger](../qa/main-integration-check-2026-11-12.md#L53). The queue reports six PRs green by name but blocked by conflicts, with roughly 2.5 hours for each replacement run; those are supplied operational observations, not a benchmark measured by this proposal.

This inspection is pinned to main `239f00583118ea11600f8ceb1d83bed4f0883430`: [DefIdentityLedger.json](../../Assets/Tests/EditMode/Fixtures/DefIdentityLedger.json) contains **118 type names and 1,964 identity rows**. Both GUIDs and `(Type, Id)` pairs are unique. A subsequent refresh of PR #1106 retained those rows in main's order and appended four golf types and fifteen identities, yielding 122 types and 1,979 rows. That fixes one conflict; it leaves the common append location in place.

The [data model's authoring rule](../architecture/data-model.md#L7) makes content independently authorable, one entity per file. Its shared test inventory now undermines that independence. Preventing this friction supports P3, A Living Working Coast, by keeping parallel content additions reviewable without weakening stable identities.

A storage migration must update this reader too. |

**Writing:** no committed append command was found in tracked filename and contract-symbol searches at the pinned revision. Both direct consumers read and assert; neither writes the fixture. Contributors currently register additions through JSON edits or ad hoc scripts. The PR #1106 refresh used an uncommitted JSON union: retain main's arrays, append branch-only rows, then reject duplicate GUIDs and `(Type, Id)` pairs. This is a repair procedure, not an existing project authoring API.

The similarly named [`tools/rig-recipes/bake-ledger.mjs`](../../tools/rig-recipes/bake-ledger.mjs#L145), `runKit`, writes `<stem>.recipe.json` and its metadata beside sprite sheets when `--write` is supplied and verification succeeds. It does **not** append Def identities. Its companion `verify-ledger.mjs` also concerns that separate recipe ledger.

The present identity test compares live assets with the current committed fixture. It does not independently compare the fixture with a protected historical revision: changing or deleting both an asset and its baseline row can evade that historical check. Every option below still needs preservation review; a future target-branch diff check could enforce no deletion or reassignment of established rows. Reordering rows must never mean replacing their identity values. Retirement remains an explicit separate decision; no automatic pruning is proposed.

## Alternatives

| Approach | Changes and conflict behavior | Identity guarantee | Migration cost |
|---|---|---|---|
| **1. Canonically sort the existing file** | Sort `Types` with ordinal comparison and rows by ordinal `(Type, Id, Guid)`; provide a formatter/checker so later additions use the same order. Distinct insertion positions can merge independently, but adjacent additions, additions to an empty array, and additions at the same final position can still conflict. Sorting reduces tail concentration; it cannot promise conflict-free merges. | Keeps every existing tuple and all current assertions. Order is not an identity rule, so the reader need not change. A formatter must reject conflicting rows rather than deduplicate or regenerate the baseline from assets. | Low implementation cost, but one large reorder diff and a one-time refresh of open ledger PRs. Need an exact before/after tuple-set comparison and canonical-output check. |
| **2. One file per full Def type** | Each file declares its type and its rows, including an explicit file for a type with no assets. Discover files rather than updating a shared manifest; flatten them for the existing assertions. Different types stop sharing a tail. Two boat-content PRs adding the same Def type can still conflict. | Keeps type coverage and every tuple if global GUID, `(Type, Id)` and cross-type checks run after flattening. Per-file checks alone would lose global protection. | Medium: split 1,964 rows across 118 type files, adapt both consumers, and prove exact set equality. Placement under `Assets` also requires Unity metadata for files and folders; a test-only directory outside `Assets` avoids that import cost. |
| **3. One file per existing asset GUID** | Store each unchanged `{ Type, Guid, Id }` in `<guid>.json`; declare types in separate per-type files, never in a central manifest. Independent additions use different paths. Competing edits to one GUID remain visible conflicts; different GUIDs reusing one id must fail semantic validation. | Keeps the original Unity GUID, full type and id; it does not mint replacement asset GUIDs. Global checks and explicit type declarations preserve uniqueness, empty-type coverage, structural exemptions and approved cross-type pairs. Enumeration must not silently overwrite duplicate keys. | Medium to high for a full split: 1,964 identity files plus 118 type declarations at this snapshot. Both consumers need a shared aggregate reader and malformed/duplicate-file checks. Metadata/import overhead depends on placement as above. No runtime or save migration. |
| **4. Generate the ledger from live assets; stop committing the result** | Generate an observed inventory through the existing reflection/`AssetDatabase` discovery and check it in CI. This removes the committed output's tail, but requires a trusted, independently retained historical baseline to compare against. | Live generation preserves current completeness and uniqueness checks. **Without that independent baseline it loses historical identity preservation:** a rename, deletion or GUID reassignment becomes the next generated truth. Comparing freshly generated assets with themselves cannot replace the contract. Retaining immutable per-identity history restores it but reintroduces a source format such as option 3. | High if equivalent history protection is required: baseline storage/versioning, deterministic export and failure/retention policy, plus both consumers. Native inventory still needs Unity; a text parser must not claim to reproduce all reflected identities. |

**Host constraint:** the host's merge does not honour custom merge drivers. Adding a `.gitattributes` union driver alone therefore does not help the merge performed there. Even a local union of JSON lines can leave broken commas, duplicate rows or conflicting bindings; a semantic identity audit is still required. The existing [`.gitattributes`](../../.gitattributes#L10) does not supply an identity-aware merger. These options work through ordinary file layout and validation rather than requiring a host driver.

## Recommendation and smallest first step

Adopt option 3 **incrementally, with the existing monolith frozen as the baseline**. Keep every existing type declaration and identity row in place. Register future identities in one small GUID-keyed file each, and future types in one file per full type name. A test-only directory outside `Assets` would avoid extra Unity imports; its final location belongs to the implementation decision. An aggregate reader combines baseline and additions in memory. No combined file or central index is committed, so it cannot become the next shared tail.

This removes the append hotspot for new content without immediately creating thousands of files. It also preserves a readable historical baseline. Additions for an existing type require only a new identity file. A new type with no assets still requires its own declaration. Reject duplicate declarations and any GUID or `(Type, Id)` repeated across baseline and additions, even if the repeated row is identical. Keep all existing structural and cross-type policies unchanged. An approved retirement would need an explicit policy change; the loader must not infer it from a missing file.

The smallest implementation step, **after this proposal is accepted**, is one migration-only PR that introduces that aggregate reader, changes both consumers to use it, freezes the then-current baseline, and defines the two addition-file shapes. It should also provide a narrow add-identity command that refuses to replace an existing binding; there is no current append tool to migrate. Do not first sort all rows or fully split the baseline. That would add refresh cost before solving new additions.

That first PR should prove:

1. An empty additions directory produces exactly the original type and identity sets. Every established `{ Type, Guid, Id }` survives unchanged; no content asset, asset metadata or save number changes.
2. Two branches adding unrelated identities merge through ordinary host-compatible file operations with no shared manifest edit. The resulting aggregate retains both additions. This is a fixture-level merge probe, not an art or gameplay acceptance test.
3. Missing recorded assets, id/type reassignment, missing registrations, malformed files, invalid filename/GUID binding, duplicate GUIDs and duplicate `(Type, Id)` pairs still fail. Preserve the exact two structural exemptions and sixteen approved plant pairs. Exercise the second reader's thirteen pinned registrations through the aggregate as well.
4. The protected target baseline cannot be edited or pruned unnoticed. Compare historical tuples against the target revision during review or a small CI check; do not rely on a hash that a contributor can update alongside a destructive edit. Native `DefIdentityContractTests` and the H7 registration test must still run by name and report nonzero case counts.

Schedule the switch at one integration boundary: finish or convert outstanding tail edits, record the final frozen baseline, then require new registrations in addition files. Convert outstanding branch-only tuples exactly once, with no interval in which one consumer reads only the monolith and another reads the aggregate. Existing successful CI remains evidence for its original head; each migrated head still needs the normal required checks. This proposal changes no CI policy and promises no exemption from a rerun.

Full per-GUID migration can wait until there is a measured need; baseline compaction should not become a recurring operation that recreates the same churn. The owner and lead architect are being asked to choose this storage direction and rollout boundary. This PR implements none of it.
