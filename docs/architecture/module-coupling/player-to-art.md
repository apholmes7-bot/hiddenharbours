# Player → Art

Audit base: `12bc04b19a2efb33e352b4eea58104f7a5599be1`. Static source review; no Unity execution or visual acceptance. This is a **permitted composition edge**, not an unrecorded feature-module dependency. [Player's asmdef:4](../../../Assets/_Project/Code/Player/HiddenHarbours.Player.asmdef#L4) references Art, and eight Player source files import it.

**Goods priority: medium for separating item identity/handling from presentation; low for rod and figure rendering.** [ADR 0055](../../adr/0055-goods-are-carried.md) requires presentation to read committed goods state. It does not require a headless lane to replace renderers, move sprite assets or change the look before the transfer model can be designed.

## Core handoff proposal

New contract names below are proposals. They do not authorize an asset move or visible change.

| Current coupling | Contract or signal that should carry it | Migration constraint |
|---|---|---|
| `CarryHands` / `CarriableCatch` → `CatchItemLibrary` | Proposed Core `ICarriedGoodsAppearance` resolves an immutable appearance/grip/facing description by species and exact size, or a presentation adapter accepts a committed item id and Core carry-pose snapshot. Art implements lookup; App supplies it. | The source of truth remains the goods registry, not the sprite/library. Preserve held pose selection, fallback behavior and grip anchors. Existing Core `ICatchHands` / `IHandsCarrier` should not acquire Art types. |
| Carriable fuel logic → `FuelLevelPresenter.Container` → `FuelContainerDef` | Proposed Core `ICarriableDefinition` exposes stable type id and data-driven lift/shape policy independently of the renderer; proposed `IGoodsContainer` carries runtime identity, contents and revision. Art reads that same definition through its own adapter. | Preserve the current asset id/GUID and serialized bindings. Do not duplicate `Carriable`/capacity/tare into a second mutable copy or silently retune them. Split gameplay contract from presentation access before adding loaded-weight limits. |
| Bucket/fuel facings and ground-sort toggles | Proposed Core `ICarriedPropPresentation` supplies available facings and accepts carry pose / support transitions. Art implements sorting and fill. Use proposed `GoodsMoved` / `GoodsLocationChanged` to invalidate committed content/support reads, not to store the only inventory copy. | Preserve current `ICarriable.ShowFacing`, `SetSort`, `OnLifted`, `OnPlaced` behavior during adapter introduction. A refused transfer must publish no successful movement or fill update. |
| Figure creation, hull renderer and character-life implementation | Keep this in explicit composition or use a proposed Core `ICharacterFigurePresentation` factory/handle, accepting existing `ICharacterFigureStand` and Core pose/carry snapshots. Art keeps renderer-specific lifetime and blink/paint details. | This is lower-priority dependency cleanup. It must not move render algorithms into the goods model or make gameplay wait for an animation/event subscriber to commit stock. |
| `SpriteLightMath.HeightScale` | Existing Core projection conventions can be exposed through a proposed shared projection read instead of a renderer utility; App supplies the exact current scale. | Equality of numerical output and owner-reviewed before/after plates are required before a later implementation changes this path. No replacement constant is proposed here. |
| `RodLineMath` | Leave the existing composition adapter in place or move the presenter implementation to Art while it consumes Core fight snapshots. If a shared pure math contract is needed, its owner must define it in Core explicitly. | No goods blocker: do not use ADR 0055 to redesign rod rendering. Preserve every current line/ripple parameter and output. |

## Findings and future failing cases

- **Gameplay availability is coupled to a rendering component.** [CarriableFuelContainer.cs:79](../../../Assets/_Project/Code/Player/CarriableFuelContainer.cs#L79) obtains its definition only through `FuelLevelPresenter`; `IsCarriable` at 83 becomes false without a configured presentation definition. This is a source-proven dependency, not a claim that current authored cans are broken. Future contract test: an engine-light carry-policy fixture with a valid goods definition but no renderer must be able to decide lift/refusal and identity. Today it cannot exercise this component's policy independently of Art.
- **The fuel Def's tooltip is stale.** [FuelContainerDef.cs:48](../../../Assets/_Project/Code/Art/FuelContainerDef.cs#L48) says nothing reads `Carriable` yet, contradicted by the Player read at 83. Failing documentation check: search the runtime consumers of the field; at least this one exists. Record the defect; do not edit the art-owned Def in this audit.
- **Missing appearance can produce an invisible owned catch.** [CarriableCatch.cs:83](../../../Assets/_Project/Code/Player/CarriableCatch.cs#L83) and 88 permit both library result and icon fallback to be absent while `_hasItem` remains true (81). This is explicitly documented fallback behavior, not an observed plate regression. Future adapter test: absent art must not drop or duplicate the item; content validation must report the missing appearance. Art acceptance remains with the owning art lane.
- **Committed-state separation still needs proof.** For a proposed item transfer rejected by capacity, identity/revision mismatch or support, verify unchanged hand/container membership and unchanged appearance request; after success, verify the presenter reads the same surviving id at its new support. This is a future acceptance case, not a test run performed by this audit.

This document changes no renderer, shader, sprite, rig, animation, palette, Def, tuned number or plate expectation. The initial goods implementation can keep these composition adapters behind Core read/command seams; visual adapter migration requires its own art-lane proof.
