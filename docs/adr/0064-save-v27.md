# ADR 0064 — Save v27: clothes, the clothing rack's sales, skills and fitted rod parts

- **Status:** Proposed (owner 2026-11-25: "Yes, plan v27". **He sees the field list,
  [`docs/design/save-v27-field-list.md`](../design/save-v27-field-list.md), before the version change merges**;
  he accepts this ADR by merging its PR.)
- **Owner:** lead-architect
- **Touches:** Core save (`SaveData`, `SaveMigration`, new `SaveRowsV27.cs` and four small row helpers). No
  gameplay code reads or writes the new fields in this PR; the clothing, rod-skill and rod-parts changes wire
  themselves to them after it lands.

## In plain words: what gets added to your save, and what happens to your existing save

**What gets added.** Four short lists:

1. **Your clothes.** Which garments you own, and which ones you have on.
2. **What the clothing rack has sold**, so a garment that sold out stays sold out after you quit and come back.
3. **Your skills.** How much experience you have with a rod (more skills can use the same list later, with no
   new save version). You ruled "yes save the rod skill" on 2026-11-25.
4. **Your fitted rod parts.** You ruled (2026-11-25) that a rod is built from a rod, a line and a reel bought
   separately and fitted per player. For each rod you have changed, the save names the line and reel on it;
   a rod you never changed keeps its own and has no entry. The parts you have bought are kept with your other
   gear, as they already are.

The clothes, skill and rod-parts lists name the player each row belongs to, so when friends join a game later,
their clothes, skills and rods go in the same lists, one more row each, without changing the save again. (The rack belongs
to the shop, not to a player.)

**What happens to your existing save.** It loads as it always did. Nothing in it is changed or lost. You start
with no store-bought garments (your outfit colours stay exactly as they are), the rack is full, your rod
skill starts at zero, and every rod has its own line and reel. The tide, wind and weather are still worked out fresh every time and are never stored.

**Going back to an older build.** An older build does not know the four lists. If you open a v27 save in an
older build and it saves, the clothes, rack sales, skill and rod fittings are lost from that file (everything else stays).
Do not go back a version with a save you care about.

## Context

Four things the player does cannot be worked out again from the world seed and the clock, so they must be
saved if they are to last:

- **Clothing** (draft #1566, `docs/design/store-clothing.md` section 4): garments bought at LeBlanc's rack are
  owned and worn per player; the rack's stock is finite. Pass 1 keeps all of it for the session only, and the
  rack is held out of the store so nothing bought can vanish on reload. The owner accepted the save change.
- **The rod skill** (draft #1568, `docs/design/rod-skill-and-tiers.md`): "add rods as a player skill that
  increases overtime". Experience grows with fish landed; the level and the help it gives are derived. Today it
  is session-only, bound to the live save object, keyed by player (`player.local` by default).
- **Fitted rod parts** (draft #1574): rods are built from a rod, a line (`fishing_line.*`) and a reel
  (`reel.*`), fitted per player (owner ruling 2026-11-25). The parts bought are presence in `OwnedGear`; what
  is fitted to which rod is not stored anywhere today.
- **Co-op** (draft #1563, ADR 0063): not part of v27, but slice 12 will give the host's save one record per
  player. v27 must not need a second migration of the same data then.

Main is at save v26 (`SaveMigration.CurrentVersion = 26`). Every earlier bump followed one pattern (v24, v25,
v26): append-only fields on `SaveData`, flat JsonUtility DTOs in a `SaveRowsVnn.cs`, one guarded step that
gives an older save empty lists, an asset-free idempotent load repair, and a `SaveMigrationVnnTests` class plus
the reflection round trip (`SavedSystemRoundTripTests`). v27 follows it exactly.

## Decision

### 1. The fields (appended to `SaveData` after `ShoppingBags`)

| Field | Type | Default (new game and migrated save) | One row per |
|---|---|---|---|
| `PlayerClothing` | `List<PlayerClothingDto>` | empty | player |
| `PlayerClothingDto.PlayerKey` | `string` | `"player.local"` | |
| `PlayerClothingDto.OwnedClothing` | `List<string>` (garment ids, `clothing.*`) | empty | |
| `PlayerClothingDto.WornClothing` | `List<string>` (garment ids) | empty | |
| `ClothingRackSales` | `List<ClothingRackSaleDto>` | empty | rack, garment, game day |
| `ClothingRackSaleDto.RackId` | `string` (`clothing_rack.*`) | `""` | |
| `ClothingRackSaleDto.ClothingId` | `string` (`clothing.*`) | `""` | |
| `ClothingRackSaleDto.Units` | `int` | 0 (a kept row has at least 1) | |
| `ClothingRackSaleDto.Day` | `int` (`DayIndex`) | 0 | |
| `PlayerSkills` | `List<PlayerSkillDto>` | empty | player and skill |
| `PlayerSkillDto.PlayerKey` | `string` | `"player.local"` | |
| `PlayerSkillDto.SkillId` | `string` (e.g. `skill.rod_fishing`) | `""` | |
| `PlayerSkillDto.Experience` | `int` | 0 | |
| `RodFittings` | `List<RodFittingDto>` | empty | player and rod changed from its own parts |
| `RodFittingDto.PlayerKey` | `string` | `"player.local"` | |
| `RodFittingDto.RodKey` | `string` (the rod's tool id, e.g. `tool.rod_coast`) | `""` | |
| `RodFittingDto.LineId` | `string` (`fishing_line.*`; empty = the rod's own line) | `""` | |
| `RodFittingDto.ReelId` | `string` (`reel.*`; empty = the rod's own reel) | `""` | |

Ids only, never content: what a garment looks like, its slot and its effects, and a skill's curve, are read
from their Defs, so retuning content moves every save with it (rule 2, rule 6). Ids are append-only and stable
(the project conventions); the save never rewrites one.

**Worn is a list of ids, not one field per slot.** The slot belongs to the garment's Def; the save has no
content to check it against. The wardrobe that writes the row keeps one garment per slot, and settles a row
that breaks it on load (the last garment named for a slot is the one he has on). A per-slot layout would put
the slot list in the save and need a new version whenever a slot is added.

**The rack saves what it sold, never its count.** Stock left = the rack Def's stock less every unit on its
rows, so retuning a rack's stock moves every save. Rows carry the day so a later restock rule can count only
recent sales without another version. Racks belong to the world, not a player: no player key (shared purse,
co-op ruling).

**Skills save experience, never the level** (rule 5: nothing derived is stored). One list for every skill, so a
second skill is a new Def and a new row, no new version.

**A fitting saves only what was changed.** An empty part id means the rod's own default part, so a rod never
fitted has no row and a rod put back to both defaults loses its row. The parts he has **bought** stay where
bought gear already lives, the `OwnedGear` presence list: no new field for that. Spare lines used up one at a
time would need counted stock, which `OwnedGear` cannot hold; **consumable spare lines are not in v27.** The
rod's combined stats are derived from its parts' Defs, never saved.

### 2. Where the code sits

- `Core/Save/SaveRowsV27.cs`: `SavePlayerKeys` (`Local = "player.local"`, `Normalise`), `PlayerClothingDto`,
  `ClothingRackSaleDto`, `PlayerSkillDto`.
- `Core/Save/PlayerClothingRows.cs`: `Owned(save, key)`, `Worn(save, key)`, `Write(save, key, owned, worn)`.
- `Core/Save/ClothingRackSaleRows.cs`: `Sold(save, rack, garment)`, `Record(save, rack, garment, units, day)`.
- `Core/Save/PlayerSkillRows.cs`: `Experience(save, key, skill)`, `SetExperience(save, key, skill, xp)`.
- `Core/Save/RodFittingRows.cs`: `LineOf(save, key, rod, partExists)`, `ReelOf(save, key, rod, partExists)`,
  `Fit(save, key, rod, lineId, reelId)`. `partExists` is an optional check the caller passes from its Defs: an
  id with no Def reads as the default part while the row keeps it as written.

All static, stateless and null-safe (a null save reads empty or zero, a write to it does nothing), in the
`SupplyLocker` / `ShoppingBagContents` style. Plain strings and ints only, so this PR depends on none of the
clothing, rod-skill and rod-parts branches, and neither of them needs anything else from Core to save.

### 3. The migration from 26

`if (SchemaVersion < 27)`: the four lists are set empty and the version stamped 27. Nothing is transformed and
nothing else moves (pinned by a test that walks a loaded v26 file through the step again and compares the whole
JSON text). An older save therefore loads with **no garments owned or worn** (`WornOutfitId`, his outfit
colours, is untouched), **every rack full**, **every skill at zero**, and **every rod on its own parts**. Nothing is invented and nothing lost.

### 4. The load repair (asset-free, idempotent; never takes away what he owns or earned)

- Clothes: drop a null row; an empty key is the local player; drop empty ids and repeats; a worn id missing
  from owned is **added** to owned (he was wearing it); rows for one player fold into the first, lists joined.
  No id is dropped for being unknown (the wardrobe skips an id it cannot find, and it comes back if the
  garment ships again).
- Rack sales: drop a row with no rack or garment, units under 1 or a negative day; sort by (day, rack, garment);
  fold equal rows, units added (so the rack never reads fuller than it is).
- Skills: drop a row with no skill id; an empty key is the local player; negative experience reads 0; two rows
  for one player and skill keep the **larger** (two copies are the same experience, not twice as much).
- Rod fittings: drop a row with no rod key; an empty key is the local player; a null part reads empty (the
  default); two rows for one player and rod fold into the first, a later row only filling a part the first
  left at default; a row with both parts at default is dropped. An unknown part id is kept as written (ids
  are append-only, and it comes back if the part ships again); `RodFittingRows` reads it as the default when
  the caller says its Def is missing.

The row helpers write exactly what the repair would leave, so save, load, save writes the same bytes.

### 5. Recomputed, therefore not saved

Unchanged by v27: tide, wind, weather, sea state, fish schools, the rod skill's level and bonus, a garment's
effects and slot, a rack's stock count, a fitted rod's combined stats. `SavedSystemRoundTripTests.SaveSchema_RecursivelyExcludesTideWindAndWeather`
still walks every field, the new ones included.

### 6. Forward shape for co-op (no second migration of this data)

All three per-player lists are **rows keyed by a player key from day one**, not single fields on `SaveData`. Today
the save holds one player, `player.local` (the save's own player; in a hosted game, the host), which is the
key the wardrobe (`ClothingPlayers.Local`) and the rod-skill book (`RodSkillBook.LocalPlayerKey`) already use.

When co-op slice 12 adds one record per player (ADR 0063), it adds a list of player records (name, look, beds,
held things) **keyed by the same player key**. Clothes, skills and rod fittings stay where v27 puts them and are found by
key; a guest is only more rows. Nothing in v27 is moved or rewritten then. Two rules make that hold, and the
co-op step must keep them:

1. A player key is a stable id: never reused, never renamed. Guest keys are minted from a saved counter
   (rule 5: no random ids), the way `NextSpecialOrderNumber` mints order numbers.
2. Co-op must **not** nest these lists inside its player record. Joining by key is the design; nesting would be
   the second migration v27 avoids.

The rod-skill branch proposed `{ SkillId; Experience }` with no player key. v27 adds `PlayerKey` because the
skill book is already per player and a guest's skill must be saved on the host (owner ruling 2026-11-25): a
row without a key would need a second format change in slice 12 to say whose it is.

### 6a. Further groups joining v27 before it merges

The fitted rod parts joined v27 this way (group C). Version 27 stays open until this PR merges: a further
group (co-op guest records if they are ready in time) is added as more lists inside the same `if (SchemaVersion < 27)` step, each
set empty for an older save, with its own repair and tests, and no second bump. Rules for any group that joins:

1. **Per-player data is a list of rows carrying `PlayerKey`** (section 6), never a field on `SaveData` and never
   nested inside another group's row.
2. **Ids, not content**: a fitted part is named by its Def id (and an instance id where one object is meant),
   never by its numbers; the rod's combined stats are derived, never saved.
3. **An older save starts the list empty** and loses nothing.

After this PR merges, anything else is version 28.

### 7. Both save files

The demo keeps its own file (draft #1510: `demo/savegame.json` beside the full game's, same name, same
`SaveStore` read and write, same JSON). v27 is a format, not a file, so both files migrate and round-trip the
same way; a test writes and reads a v27 save at both paths in a temporary folder, and reads a v26 file placed
at the demo path.

### 8. Size cost

Pretty-printed JSON, approximate:

- A v26 save migrated, nothing used yet: about 100 bytes (four empty lists).
- Every garment pass 1 ships owned (7) and six worn: about 0.7 KB.
- The rack: about 170 bytes per row. Rows fold per garment per day, so a demo week is a handful of rows
  (under 1 KB); the worst case, every garment selling every day of the week, is about 8 KB.
- The rod skill: about 130 bytes per player.
- Rod fittings: about 170 bytes per rod changed, per player; a handful of rows at most.

## Consequences

- One version bump, four lists, no behaviour change. Clothing can put its rack in the store once it writes the
  rows; the rod skill stops resetting on load once it reads and writes its row; fitted rods keep their parts once
  the fitting code reads and writes its rows.
- Opening a v27 save in an older build loses the four lists (stated to the owner above).
- Later skills and garments need no new version; a guest needs no new version for clothes, skills or rod fittings.

## Alternatives considered

- **Garments in `OwnedGear`.** Rejected (store-clothing.md section 4): gear is presence-only tools; no worn
  state; no player.
- **Rack sales in `StorePurchases`.** Rejected: those rows are rewritten whole per shop by the shelves.
- **Per-player fields directly on `SaveData`** (`OwnedClothing`, `WornClothing`, `RodExperience`). Smallest
  today, but co-op would have to move them into player records: the second migration this ADR avoids.
- **One `PlayerRecord` list now holding clothes and skills.** Rejected: it would pre-decide co-op's record
  before ADR 0063 is accepted, and still mean moving name, look and the rest later.
