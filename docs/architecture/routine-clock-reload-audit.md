# Routine and scheduled-trip clock audit

Original audit base: `d9d4b8558aaa77b49b6bad9dbb35345d2059814c`; refreshed against main `12bc04b19a2efb33e352b4eea58104f7a5599be1`. Scope includes the villager routine engine, scheduled road trips, ambient fleet, conversation overlays, and the newly integrated NPC pot fleet and beach-day routines. This is a source audit and test addition; production behavior is unchanged. Line references in the original findings below refer to the original base; the refresh checks identify current members by name.

The clock samplers can reconstruct their answers without earlier ticks. That statement applies to the plan, with fixed authored content and day length. It does not establish that every live presenter or interaction has identical state after loading.

The integrated presenters add these explicit limits to F1–F14:

- `VillagerRoutine.RefreshDay` invalidates on day, day-source reference, version, or seconds per game hour. The base plan still detects seed changes on the shelter poll. A cached day-source failure is not automatically retried until an invalidation input changes.
- `BeachLifeDirector.Version` tracks terrain/service identity, tide profile, and library reload. Its rank is taken from a sorted, deduplicated roster of currently discovered villagers, refreshed by unscaled time. The rank can therefore depend on activation and discovery timing; sorting does not make an incomplete roster complete. Same-input beach-plan proof does not establish identical cold-load versus retained-presenter behavior.
- Beach gathering registrations, speech progress, and polling remain transient. They do not acquire a save/load contract from the sampler tests.
- `NpcPotBoats.Tick` rebuilds today, yesterday, catch, and landing when day, seed, or day length changes. A same-day clock seek resamples those plans. Auto-binding, terrain/water probes, and rope/presentation state use a slow real-time tick; content or environment replacement alone is not part of its plan cache key. The source check makes no first-frame or pixel-equality promise.

These are documented boundaries for follow-up decisions, not changes to save format, native lifecycle, routines, or presentation. No existing test assertion was removed or weakened.

## State outside the seed and clock

These findings describe source behavior and reload risks. They do not prescribe new save fields or accept a presentation change.

| Finding | Read or retained state | Reload consequence and disposition |
|---|---|---|
| F1 — conversation hold | `VillagerRoutine.cs:110,199,258` reads current NPC/player transforms and `ConversationHold` phase/position, then advances catch-up with scaled delta time. | A held or catching-up villager differs from the base clock pose by design. Disable cancels the hold; an in-place clock restore does not itself call that cancellation. **Park implementation:** decide whether loading always ends interactions. |
| F2 — reveal and seed polling | `VillagerRoutine.cs:207,321` reads unscaled time, a cached next-check timestamp, the active hold, and `BuildingInterior.IsInside`. | Visibility/talkability depends on the player and polling phase. A same-component seed change is detected on the shelter tick and replanned on the following update. **Park implementation:** define the restore boundary and immediate refresh requirement. |
| F3 — activation and missing services | `VillagerRoutine.cs:149,228` resets `_planned`, but retains `_plan`; a missing environment returns before replacing it. A failed non-null-service build is cached. | A re-enabled component can still sample its previous plan while the seed service is absent. A failed build does not retry merely because station/content availability improves. Cold components with no previous plan wait. **Park implementation:** select an explicit activation/retry policy. |
| F4 — captured authored geometry | `RoutinePlanner.cs:65,154,176` reads station/lane tables and live interior door geometry at build time. | Reconstruction matches when the same authored inputs are available. Mid-session edits or incomplete scene wiring are additional inputs; changing their handling is outside this audit. |
| F5 — conversation history | `NpcConversationDirector.cs:264,332` retains ran-on-day and last-run-time dictionaries, the current conversation, line index, speech id, and speaker references. | A fresh director forgets earlier exchanges; a retained director keeps them across a clock seek. `ForgetSessionState` exists, but this base has no production caller and no `GameLoaded` subscription. **Park implementation:** decide replay/skip behavior without adding a save format here. |
| F6 — conversation availability | `NpcConversationDirector.cs:187,228,275,320` uses unscaled polling, the current region, discovered active objects/station table, current participant transforms, talking/walking flags, and speech-ended events. | A due minute does not uniquely determine whether an exchange starts or which line is in progress. Duplicate discovered NPC ids overwrite by discovery order; these require invalid-content handling, not a new random seed. |
| F7 — seat/trailer ownership | `ScheduledTrip.cs:243,299` reads seat claims, actual coupling, towed-body holds, and local ownership flags. | A clock-derived trip can fail to acquire a live resource. Machine/driver poses are applied before seat/trailer claims; claim refusal does not undo those poses. Disable releases claims and reveals the driver. **Park implementation:** decide how a loaded trip competes with an occupied resource. |
| F8 — trailer plan input and readiness | `ScheduledTrip.cs:341,426` sets `_planned` and builds from mesh/skinning availability, wheel/pin metadata, and the trailer's current world position/heading. | Replanning mid-trip can supply a moved trailer as the starting bay and refuse or change the plan. A trailer not yet skinned can choose bobtail/stay-home once and remain cached until re-enable or day-length change. **Park implementation:** define a stable authored starting pose and readiness retry rule. |
| F9 — road timetable/day length | `ScheduledTrip.cs:154,183,332` rebuilds on enable or changed seconds per hour; fixed routes and trip assets are otherwise cached. | Same spec and clock reconstruct the full road pose, including towing fields. A live day-length change intentionally defers replanning for an update. This audit preserves that behavior. |
| F10 — integrated ambient hulls | `AmbientFleetPresenter.cs:444,498,529,537,546` retains positions/headings/speed/holding/depth correction, reads neighboring boats and player/buoy positions, and integrates steering. | A fresh day plan snaps to the clock's current target and sets holding/speed state; an uninterrupted boat can be between targets or avoiding something. Exact hull position is **not** reconstructed solely from seed and clock. **Park implementation:** choose deterministic reconstruction versus an explicitly interactive transient trajectory. |
| F11 — ambient seek/invalidation | `AmbientFleetPresenter.cs:212,230,413,472` retains previous game time and day index, and caches terrain/water inputs. | A backward seek clamps delta to zero but retains the trajectory; a forward seek can produce a large integration step. Automatic replanning checks day index, not a replacement seed/service/day length within that day. **Park implementation:** specify load invalidation before changing the presenter. |
| F12 — ambient scene/readiness | `AmbientFleetPresenter.cs:202,217,237` uses real-time gate/probe cadence, active scene, registered services, and a discovered player boat. | Activation and fresh probe timing depend on scene/service ordering. Tidal depth comes from the current environment and terrain; null-service fallbacks are additional transient inputs. |
| F13 — player buoy event buffer | `AmbientFleetPresenter.cs:177,190,540` retains a dictionary populated by trap placement/removal events and enumerates it for avoidance. | Avoidance depends on player actions and registration/restore event order. A fresh subscriber needs placement facts replayed or rebuilt; seed/time alone cannot recreate them. No save or restore protocol changes are made here. |
| F14 — buoy transition progress | `AmbientFleetPresenter.cs:456,567,626` stores hidden/rising/afloat/sinking state and progress; initialization snaps binary presence and later frames animate toward it. | Binary buoy presence matches the clock; a mid-transition picture need not match after load. **Park any presentation change:** it requires the relevant art lane and evidence. |

`Core/Save/SaveRestore.cs:57,65,72` seeks the clock and publishes `GameLoaded`; none of the three presenters above subscribes to that event. A cold reconstruction, region re-enable, and an in-place restore are therefore distinct cases. This audit changes neither the saved format nor those lifecycle rules.

## Added clock contracts and proof limits

- `RoutinePlanTests.LoadAtEveryHour_MatchesMeasuredWalkWithoutEarlierTicks`: two day lengths, all hours, fractional hours, midnight/multi-day wrapping, departure/arrival edges, and an independent 120 m / 2 m/s oracle. Every pose field is checked.
- `RoutinePlanTests.ReloadAtEveryHourAndBlockTransition_MatchesTheClockWithoutReplay`: three seeds; rebuilds the existing planner fixture at every hour/fraction and on both sides of walk/departure transitions, comparing all pose fields after non-monotonic prior sampling.
- `VehicleTripPlanTests.ReloadAtEveryHourAndTripTransition_MatchesTheClockWithoutReplay`: ordinary and overnight timetables, all hours/fractions, every stage boundary and midpoint, all machine/driver/trailer fields.
- `VehicleTowingTripTests.ReloadAtEveryHourAndCouplingTransition_MatchesEveryClockPoseField`: the existing towing fixture, each hour and all ten coupling/driving/alighting/resting stage boundaries and midpoints, including trailer pose, coupling, and landing gear.
- `AmbientFleetScheduleTests.LoadAtEveryHourAndBuoyFlip_MatchesAnIndependentEventReplay`: two phases, each quarter-hour and exact place/haul boundaries, compared with an independent replay that toggles each completed visit.

All four changed test files compile with the pinned editor compiler. Four new cases involving Unity object creation or AssetDatabase need Unity execution in CI. No local editor or lifecycle run is claimed, and no test claims that F10's integrated hull positions are clock-pure. No existing assertion was removed or weakened.
